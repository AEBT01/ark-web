# 页面操作（browser-ops）

操作类任务的本质是：**找到目标 → 动作 → 核实**。三步缺一不可。

## 1. 定位
- 描述性目标（"那条说太棒了的评论的点赞按钮"）→ `semantic_find {query}`，从返回的 `hits[].id` 拿到内容块，`interactives[]` 会列出块内可交互控件。
- 结构明确的目标（"侧边栏的搜索框"）→ `query_all` 或 `snapshot` 看结构。
- 都找不到 → 用 `read_text` 通读，再决定。不要盲目猜选择器。

## 2. 动作
- 优先 `semantic_click`（语义层会先滚动到视口内再点，且对高风险词自动请示）。
- 表单类用 `semantic_fill`（按 label 定位输入框），不要用坐标。
- 页面未加载完时不动作：`wait_load` 或 `wait_for` 先等关键元素出现。

## 3. 核实（多数失误发生在这里）
- 点击后用 `semantic_find` 或 `query_all` 确认状态真的变了（按钮变成"已加入"、出现提示条、计数 +1）。
- 页面无可见变化时，检查 `console_logs` 与 `network_log`：请求发出去了吗？返回了什么？
- **页面没有反馈 ≠ 动作失败**：有的站点点击后由后台异步处理。核实后如实描述"看到了什么、没看到什么"，不要编造成功。

## 4. 收尾
- 达成目标 → `finish {answer, summary}`。答复里给用户可验证的证据（"按钮现在显示已加入"），而不是过程流水账。
- 反复尝试（同一步骤 ≥3 次）仍不成功 → 换定位方式；仍不行 → `give_up` 说明卡在哪一步、试过什么。

## 常见坑
- 弹窗/遮罩挡住目标：先看 `snapshot` 是否有对话框层，用 `dialog` 端点处理。
- 元素在 iframe 里：`semantic_find` 覆盖不到 iframe，用 `query_all` + frame 相关端点。
- 点击"成功"但状态没变：可能是前端校验拦截（看 console 报错），如实报告，不要重试到成功为止。
